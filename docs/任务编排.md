## 工作原则

1. 任务拆解必须服务于执行，不要复述计划，也不要输出泛化任务，如“完善系统”“联调优化”“补充细节”。
2. 每个任务都必须是一个可独立推进、可单独验收、可明确交付的工作单元；避免把多个关注点硬塞进同一任务。
3. 按真实依赖顺序编排，优先遵循“资源准备/契约对齐 -> 数据与能力建设 -> 页面或流程实现 -> 联调验证 -> 交付验收”。
4. 不要凭空新增执行计划里没有的功能；如果为了落地必须补齐前置项，只能补“必要前置任务”，不能扩展需求范围。
5. 允许做“最小必要推断”来保证任务可编排；所有推断都必须标注 `【推断】`。
6. 任务描述要面向交付结果，而不是面向动作口号；读完任务后应能直接知道完成标准是什么。
7. 当任务规模较大、依赖链较长、涉及多模块或明显存在前后置关系时，必须按阶段（stage）拆解，而不是输出一个扁平任务列表。
8. 阶段划分必须服务于执行推进，避免按团队、角色或技术名词机械分组；优先按“可交付里程碑”和“依赖闭环”分阶段。

## 编排要求

请严格按照以下结构输出：

### 1. 阶段概览

- 先给出整体阶段划分结果，按执行顺序列出。
- 每个阶段必须包含：
  - 阶段ID：建议使用 `S1`、`S2`、`S3` 形式。
  - 阶段名称：必须体现该阶段的主要交付目标。
  - 阶段目标：说明该阶段完成后，系统或项目进入什么状态。
  - 阶段包含范围：概括本阶段承载的任务边界。
- 如果任务规模较小，允许只输出 1 个阶段；但只要存在明显前后依赖，就仍然要进行阶段划分。

### 2. 分阶段任务列表

- 按阶段输出任务，而不是输出单一扁平列表。
- 每个任务必须满足：
  - 名称清晰，能体现目标产出，而不是笼统动作。
  - 描述只写该任务自身范围，不把后续任务内容提前合并。
  - 产出必须是可验证对象，如页面、接口、数据结构、测试用例、配置项、脚本、文档化契约等。
  - 依赖只填写“直接前置任务”，不要重复祖先依赖；无依赖则写“无”。
  - 如该任务强依赖某个 Figma MCP URL，可在依赖中一并写出。
  - 如某任务依赖特定资源、接口、文档、设计稿或外部输入，必须在“资源”字段中明确列出。
  - 如任务依赖的后端接口显式配置了 `Host`，必须在“资源”字段中单独写明；`Host` 为可选项，但一旦配置，表示该接口走独立 Host，不再请求通用的 host。
  - 验收必须可操作、可观察、可判定，不要使用主观措辞。
- 每个阶段使用以下格式：

#### [阶段ID] [阶段名称]

- 阶段目标：[1-2 句话说明本阶段的完成状态]
- 阶段依赖：[直接依赖的阶段ID；无则填“无”]

- 本阶段任务使用以下格式：

- [ ] **[任务ID]** [任务名称]
  - 描述：[1-2 句话说明该任务具体做什么，以及边界是什么]
  - 产出：[可验证的交付物]
  - 依赖：[直接依赖的任务ID；无则填“无”；如需 UI 依据可附 Figma MCP URL]
  - 资源：[与该任务直接相关的资源，如 Figma、接口、数据表、配置、脚本、文档；如接口有独立 Host 必须写明；无则填“无”]
  - 验收：[1-2 句话说明如何判断该任务完成]

### 3. 单元测试覆盖

- 只列出需要通过单元测试保护的核心模块、函数或规则。
- 如果某部分更适合集成验证而不适合单测，不要强行写入本节。
- 如无需新增单元测试，明确写“无新增单元测试要求”。

### 4. 集成测试覆盖

- 列出需要验证的跨模块、跨接口、跨数据流转场景。
- 重点关注接口契约、状态流转、权限校验、第三方依赖对接等内容。
- 如无需新增集成测试，明确写“无新增集成测试要求”。

### 5. 端到端验证

- 列出需要人工或 E2E 验证的核心用户场景，优先覆盖主流程与高风险异常流程。
- 每条场景应体现起点、关键操作和预期结果。
- 如无需新增端到端验证，明确写“无新增端到端验证要求”。
