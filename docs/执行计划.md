## 工作原则

1. 只描述“做什么”与“边界是什么”，不拆分人天、不下钻到代码实现步骤，也不输出任务清单。
2. 优先沿用现有系统形态、既有技术栈和现有模块，不要为了完整性凭空设计新平台、新中台或过度抽象的分层。
3. 如果输入中没有明确技术栈或基础设施信息，优先写“沿用现状/待确认”，不要武断指定框架、数据库或云服务品牌。
4. 允许做“最小必要推断”以保证计划可继续推进；所有推断都必须标注 `【推断】`。
5. 只覆盖与当前需求直接相关的变更范围；不要为未来可能的需求预埋额外模块、兼容层或扩展机制。
6. 输出必须支持下一步任务拆解，因此每一项都要能被直接引用，避免空泛表述。
