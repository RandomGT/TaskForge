## 需求描述

[在此处粘贴用户需求]

## 工作原则

1. 只基于输入信息做判断，优先提炼显式需求，不要发明页面、流程、角色、业务规则或成功指标。
2. 允许做“最小必要推断”，仅用于让输出可以继续推进；所有推断都必须显式标注 `【推断】`。
3. 不输出任何技术实现细节，包括但不限于技术选型、数据库设计、接口实现方案、组件实现方式。
4. 如果存在关键信息缺失，不要擅自补全；应写入“待澄清项”，但仍尽量给出可暂行的边界定义。
5. 输出内容必须能被下一阶段直接引用，因此每一项都要具体、可验证、可追踪，避免空泛描述。
6. 如果用户提供了 Figma URL、接口说明、现有系统约束或其他外部资产，必须结构化提取，不要遗漏。

## 拆解要求

请严格按照以下结构输出：

### 1. 核心意图

- 用一句话概括该需求要解决的根本问题。
- 不要复述表面功能，要指出真正的业务目标或用户价值。

### 2. 用户故事

- 仅保留对范围界定有帮助的关键场景，避免为了“凑全”而拆出重复场景。
- 按以下格式输出：
  - 作为 [角色]，我想要 [功能]，以便 [价值]
- 如果角色不明确，可使用“用户”；如果是合理推断出的角色，需标注 `【推断】`。

### 3. 功能边界

#### 必须包含（Must Have）

- 只列出需求中明确要求、或直接决定是否交付成功的功能点。

#### 可选但未确认（Optional / Unconfirmed）

- 仅当需求中存在明显暗示、但尚未明确承诺时列出。
- 每条都必须标注 `【推断】`，避免与 Must Have 混淆。

#### 不应包含（Out of Scope）

- 列出需求已明确排除、或根据上下文可以确认本轮不纳入的内容。
- 如果某项只是“用户未提及”，不要强行列出；仅在容易被误解为范围内时才写出以防歧义。

### 4. 验收标准

- 每条标准必须可客观验证，且只描述一个可观察结果。
- 使用以下格式：
  - 当 [前置条件]，且用户 [执行操作]，则系统 [预期结果]
- 不要使用“体验良好”“响应合理”“界面友好”等主观表述。

### 5. 隐含约束

- 仅列出能从需求中合理推断出的非功能性约束，例如性能、安全、权限、兼容性、合规、交互一致性。
- 如果某项约束来自推断而不是显式要求，需标注 `【推断】`。
- 如无明确可提炼内容，输出“无隐含约束”。

### 6. 待澄清项

- 列出需求中模糊、矛盾、缺失或会显著影响方案边界的关键信息。
- 每条必须使用以下格式：
  - [问题]｜为什么重要：[说明对范围/验收/实现的影响]｜是否必须澄清：[必须澄清/非必须澄清]
- 只有真正影响后续规划的信息才放入本节，避免提出低价值问题。

### 7. 资产

- 如果用户提供了 Figma MCP URL，请按以下格式列出：
  - [页面]-[模块]-[FigmaMCP URL]
- 如果用户提供了后端接口，请按以下格式列出：
  - [接口详细信息]-[接口说明]
- 如果用户提供了其他资产（如图标、多媒体、文案、规范链接、第三方系统入口等），按以下格式列出：
  - [资产类型]-[资产名称]-[用途或说明]
- 如果没有相关资产，输出“无”。

## 输出格式

仅输出上述七个部分。
每个一级部分必须以 `###` 开头；三级分组仅用于“功能边界”内部。
不输出分析过程、免责声明、额外建议或任何结构外内容。
